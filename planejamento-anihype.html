01 — Produto

O que é o AniHype

Uma plataforma social premium de anime sazonal. Mais Letterboxd do que banco de dados.

Missão do produto: Não competir com AniList ou MAL em quantidade de dados. Competir em comunidade, emoção e experiência visual.
A sensação que o usuário deve ter: "Esse site está vivo. Tem gente aqui."

03 — Roadmap

O que falta construir

Features ordenadas por impacto. Cada item = back + front completo. Um dev, uma feature.

🔴 Crítico — sem isso o produto não vive

1

Popular o banco com animes da temporada atual

Rodar npm run sync:season ou admin → Importar Temporada. Sem isso a home e o calendário ficam completamente vazios. Não é código novo — é operação.

2

Deploy em staging ou produção

Sem um ambiente acessível não dá para testar com usuários reais nem dividir tarefas com confiança. Precisa de VPS ou serviço cloud (Railway, Render, Hetzner) + Docker Compose completo + domínio + SSL.

🟣 Alta Prioridade — alto impacto, implementar logo

3

Editar perfil + upload de avatar ⬛ banco pronto

Usuário não consegue mudar nada depois de criar a conta. Envolve: endpoint PATCH /users/me, integração com storage externo (Cloudflare R2 ou S3) para avatar, e página/modal /configuracoes no frontend.

4

Recuperar senha ⬛ banco pronto

Tabela password_reset_tokens já existe. Falta: endpoint POST /auth/forgot-password, envio de e-mail com token (SMTP / Resend / SendGrid), endpoint POST /auth/reset-password e tela no frontend.

5

Ranking de animes ⚡ fácil

Página /ranking com os animes mais bem avaliados. Banco já tem índice em ratingAverage + ratingCount. Endpoint simples + nova página no frontend. Alto impacto visual, esforço pequeno.

6

Busca global novo endpoint

Endpoint GET /search?q= retornando anime + usuário em uma busca só. Hoje a busca só funciona no catálogo /anime. Decisão de UX: barra no header ou página dedicada /search?

7

CI/CD com GitHub Actions

Arquivo .github/workflows/ci.yml rodando lint + typecheck + build em todo PR. Evita que código quebrado entre na main. Pré-requisito para trabalhar em equipe com segurança.

05 — Colaboração

Regras do Time

Simples, mas evitam horas de debug e conflito de merge desnecessários.

1

Um branch por feature: feature/nome-da-feature. Nunca commitar direto na main sem PR.

2

Antes de mexer em schema.prisma: avisa o time no chat. Todos precisam dar git pull e rodar a migration antes de continuar.

3

Antes de mexer em app.module.ts: avisa antes. É o arquivo que mais gera conflito de merge no backend.

4

Antes de abrir PR: rodar npm run type-check. Não abrir PR com erro de TypeScript.

5

services/api.ts e types/api.ts: avisar no chat antes de editar — todo dev mexe nesses arquivos, conflito fácil.

6

Nunca commitar .env: nem da API nem da web. Usar sempre o .env.example como referência para novos devs.

7

Zero hardcode: URLs, segredos e credenciais sempre em variáveis de ambiente. Nunca no código.
